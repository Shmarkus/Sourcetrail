# `st serve`: warm index and file watcher (Phase 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring a query from ~0.9 s to well under 200 ms when an opt-in server is running, and make the cold path cheaper for when none is.

**Architecture:**
- **Cold path first.** Measured on a 2k-file Spring service, a cold `st refs Scheduled` takes ~0.95 s:
  - setup (project, lock, freshness walk): 70 ms;
  - `PersistentStorage::buildCaches()`: 560–620 ms, of which the GUI's member-edge order is ~290 ms;
  - name lookup: ~200 ms for a library name (the fallback pass), 4 ms for a project name;
  - walk: 30 ms;
  - printing and teardown: ~80 ms.
- **One code path for both modes.** All of `run()` moves into a `runCommand(request, io, cache)` that writes to the given streams and gets its storage from an `IndexCache`.
  - The cold `st` makes a fresh cache per process.
  - `st serve` keeps one cache alive and runs the same function for each request.
  - Output therefore cannot drift between the two modes.
- **Freshness stays per request.** Under the project lock, each request still runs the freshness walk (~40 ms). A stale index is still refreshed before answering. The warm storage is reused only while the database files are unchanged on disk; otherwise it is reloaded.
  - Correctness never depends on the watcher.
  - The watcher only starts refreshes early, so the refresh is usually done before the agent's next query arrives.
- **Client.** `st` finds its project as it does now and derives the server's socket name from the canonical project path.
  - It tries to connect for at most 50 ms. On success it forwards the arguments, cwd, stdin and whether stdin is a terminal, then prints the reply.
  - Otherwise it answers cold.
  - `--no-server` and `ST_NO_SERVER=1` force the cold path.
- **Opt-in only.** Nothing starts the server except `st serve` (foreground) or `st serve --detach`. It serves one project. `st serve --stop` ends it.

**Tech Stack:** C++17, Qt5 Core and Network (`QLocalServer`/`QLocalSocket`, `QFileSystemWatcher`, `QDataStream`), Catch2, Bash smoke tests.

**Spec:** `docs/superpowers/specs/2026-10-30-sourcetrail-cli-requirements.md`. These targets drive the plan:
- startup per command under 200 ms;
- a query on an open index under 1 s;
- the "MCP server wrapper … database kept open between calls" nice-to-have, met here by a local socket.

Background: the Phase 2.5 plan is `docs/superpowers/plans/2026-10-31-st-trust.md`. The decisions recorded for Phase 3 are:
- the watcher is opt-in and never auto-started;
- it is built together with the resident process;
- it debounces bursts;
- it ignores `build/`, `.gradle/`, `.git/` and `sourcetrail_dependencies/`;
- queries keep their own freshness check as the fallback.

## Global Constraints

- Every Phase 1, 2 and 2.5 output rule still holds, and stdout carries results only.
- A query answered by the server must produce the same stdout, the same exit code and the same stderr lines as the cold path. The only addition is the notes listed in this plan.
- Exit codes are unchanged: 0, 1, 2, 3, 64, plus the existing stale, no-index and internal codes.
- The server is never started implicitly: not by `st`, not by a query, not by the indexer.
- The server never holds the project lock between requests, and never while Sourcetrail indexes.
- No new third-party dependencies. Qt Network is already linked into `Sourcetrail_cli_queries`.
- Linux is the target. Keep it compiling elsewhere by using only Qt APIs; no `#ifdef` beyond the socket path.
- Never modify the real projects under `~/Projects`. Measure on the bench copies under `~/bench/`.
- Committed files and commit messages name no private project, package or class. Use the fixture or neutral names (`com.acme.shop`).

## Review Focus

1. **A server from an older build.** After `st` is rebuilt, a still-running server must not answer. The client goes cold with one stderr note. Test: Task 3, `client answers cold when the server is from another build`.
2. **Index rewritten under a warm server.** When a refresh by cold `st`, the GUI or `Sourcetrail index` replaces or changes the database, the next request reloads instead of reading the old handle. Test: Task 2, `index cache reloads when the database file changes`; smoke in Task 3.
3. **A stale socket file.** When the server was killed, the client falls back within 50 ms, and a new `st serve` removes the dead socket and starts. Test: Task 3 smoke (`kill -9`, then a query and a restart).
4. **Stdin, terminal state and cwd forwarded faithfully.**
   - `echo key | st callers` through the server equals the cold result.
   - `st callers` with no name from a terminal gives the same usage error.
   - `st at File.java:42` resolves relative to the client's cwd, not the server's.
   - Test: Task 3 smoke equivalence table.
5. **An edit during a background refresh.** Another refresh must follow. A query must never answer from an index older than the files it was asked about. Test: Task 5, `scheduler queues another refresh when changes arrive while one runs`; the per-request freshness check is the backstop.

### Task 2: One command runner for cold and warm use

- Test: `src/cli/st/StQueryTest.cpp`.

**Interfaces:**
- Produces:
  ```cpp
  namespace st {
  struct Request {
      QStringList arguments;      // argv including argv[0]
      QString cwd;                // absolute
      bool stdinIsTerminal = true;
  };
  struct Io { std::istream& in; std::ostream& out; std::ostream& err; };

  class IndexCache {
  public:
      // The index storage with query caches built. Reuses the loaded storage while the database
      // file and its -wal/-journal files keep the same inode, size and modification time; otherwise reloads.
      PersistentStorage& storage(const ProjectSettings& settings);
      bool reusedLast() const;    // whether the last storage() call reused a loaded index
  };

  int runCommand(const Request& request, Io io, IndexCache& cache);
  }
  ```
- `runCommand` throws nothing. It maps `UsageError`, SQLite and std exceptions to the exit codes that `main` maps today, and writes the same messages to `io.err`.
- `QCommandLineParser::process` exits the process on `--help` and parse errors. Use `parse()` and print help or errors to `io.err`/`io.out` the way `process` would, with the same exit codes.

### Task 3: `st serve` and the client

**Files:**
- Create: `src/cli/st/StServer.{h,cpp}` (protocol, socket name, server loop) and `src/cli/st/StClient.{h,cpp}`.
- Modify: `src/cli/st/StMain.cpp`, `src/cli/st/StTest.cpp`, `testing/cli/st-smoke.sh`.

**Interfaces:**
- Consumes: `st::Request`, `st::Io`, `st::IndexCache`, `st::runCommand` (Task 2).
- Produces:
  ```cpp
  namespace st {
  constexpr quint32 PROTOCOL_VERSION = 1;
  // $XDG_RUNTIME_DIR, else QDir::tempPath(), + "/st-" + first 16 hex of SHA-1(canonical project path) + ".sock".
  QString serverSocketName(const FilePath& projectFile);
  // The running binary's identity: absolute path, size and mtime of QCoreApplication::applicationFilePath().
  QString buildId();

  struct WireRequest { quint32 version; QString buildId; Request request; QByteArray stdinData; };
  struct WireReply { qint32 exitCode; QByteArray out; QByteArray err; bool refused = false; QString refusal; };
  QByteArray encode(const WireRequest&);  bool decode(const QByteArray&, WireRequest*);
  QByteArray encode(const WireReply&);    bool decode(const QByteArray&, WireReply*);

  struct ServeOptions { bool watch = true; };   // Task 5 reads watch; --no-watch clears it
  int serve(const FilePath& projectFile, const ServeOptions& options, std::ostream& err);  // blocks
  // Returns the exit code, or std::nullopt when no server answered, in which case the caller runs cold.
  std::optional<int> tryServer(const FilePath& projectFile, const Request& request, std::ostream& out, std::ostream& err);
  }
  ```
- Framing: one `quint32` byte length, then the `QDataStream` payload (Qt_5_12) on each side. One request per connection.
- Server:
  - It is single-threaded and handles requests one at a time.
  - Each request sets `QDir::setCurrent(request.cwd)` for the duration of the call, so relative paths resolve against the client's directory.
  - It refuses a version or build-id mismatch, and a request whose located project isn't the served one.
  - It listens with `QLocalServer::UserAccessOption`.
  - At start it calls `QLocalServer::removeServer` for a socket nobody answers. If another server answers, it prints `st: server already running for <project>` and exits 0.
- Client:
  - It skips the server when the command is `serve`, `--no-server` is given or `ST_NO_SERVER=1`.
  - It connects with a 50 ms timeout.
  - When stdin is not a terminal, it sends stdin read to EOF.
  - On a refusal it prints `st: server <refusal>; answering without it` and returns nullopt. If the server drops the connection before replying, it prints `st: server did not answer; answering without it` and returns nullopt.
- Status: `st status` gains a last line, `server\trunning` or `server\toff`. Through the server it is `running`; on the cold path `st` probes the socket (50 ms) and prints what it finds.

- [ ] **Step 1: Failing unit tests.**
  - `wire request and reply round-trip`: covers non-ASCII args and cwd, empty stdin and 1 MB stdin.
  - `socket name is stable, per project, and short`: the same path gives the same name, two paths give different names, the length is ≤ 100, and a symlinked path equals the canonical one.
  - `client answers cold when the server is from another build`: an in-process `QLocalServer` replies `refused` with "is from another build". `tryServer` returns nullopt, and `err` has the note.
- [ ] **Step 2: Implement the server, the client and `st serve` in the foreground.**
- [ ] **Step 3: Smoke.** Start `st serve` on the fixture in the background, wait for the socket, then:
  - **Equivalence:** for each command the smoke script already runs, and for these four inputs, compare stdout, stderr (minus the `server` status line) and the exit code between `st …` and `ST_NO_SERVER=1 st …`:
    - a piped `echo key | st callers`;
    - `st at` with a path relative to a subdirectory cwd;
    - an ambiguous name (exit 2);
    - an unknown name (exit 3).
  - **Freshness:** edit a fixture file and query through the server. The answer must show the change, and stderr must carry `refreshed N files`.
  - **Rewritten index:** run `ST_NO_SERVER=1 st` after another edit (a cold refresh), then query through the server. The answer must show the change.
  - **Stale socket:** `kill -9` the server, then a query answers cold within 1 s total. A new `st serve` starts.
- [ ] **Step 4: Measure** on the bench project with the server running, median of 10, for `st status`, `st refs Scheduled` and one `callers` query. Target under 200 ms each.

### Task 4: `--detach` and `--stop`

**Files:** `src/cli/st/StServer.cpp`, `src/cli/st/StMain.cpp`, `testing/cli/st-smoke.sh`.

**Interfaces:**
- `st serve --detach`:
  - It starts `st serve --project <file>` with `QProcess::startDetached`, with stdout and stderr going to `<project dir>/.st-serve.log` (truncated at start).
  - It waits up to 30 s for the socket to answer.
  - It prints `st: server running for <project> (pid N)` and exits 0, or exits `EXIT_INTERNAL` with the log's last 20 lines on stderr.

- A stop request is a `WireRequest` whose arguments are `{"st", "serve", "--stop"}`.

### Task 5: Watcher and background refresh

**Files:**
- Create: `src/cli/st/StWatch.{h,cpp}`.
- Modify: `src/cli/st/StServer.cpp`, `src/cli/st/StCommand.cpp` (a refresh that is already running is waited for, not started twice), `src/cli/st/StTest.cpp`, `testing/cli/st-smoke.sh`.

**Interfaces:**
- Produces:
  ```cpp
  namespace st {
  // Pure debounce state: no timers, no Qt, so it can be tested without an event loop.
  class RefreshScheduler {
  public:
      explicit RefreshScheduler(qint64 quietMs = 500);
      void changed(qint64 nowMs);          // a watched path changed
      bool due(qint64 nowMs) const;        // changes pending, none for quietMs, no refresh running
      void started();                      // pending changes are now being refreshed
      void finished();                     // the running refresh ended (successfully or not)
      bool pending() const;
      bool running() const;
  };
  // Directories and files to watch: every source root, every directory holding an indexed file, every
  // indexed file, and the Gradle build files; never anything under build/, .gradle/, .git/ or
  // sourcetrail_dependencies/. Above 20000 paths, files are dropped and only directories are watched.
  std::vector<QString> watchPaths(const ProjectSettings& settings, const std::vector<FilePath>& indexedFiles);
  }
  ```
- Server: a `QFileSystemWatcher` over `watchPaths(...)`, with a 100 ms `QTimer` polling `due()`.
  - When due, it runs the same refresh `runCommand` would, as an async `QProcess`, plus `recordRefresh`. It does not hold the project lock; the indexer takes it.
  - On finish it reloads the `IndexCache` eagerly and re-adds paths that editors replaced, since an atomic save drops the watch.
  - A request that arrives while a background refresh runs waits for it (`waitForFinished`) before its own freshness check, and adds `st: waited Xs for the background refresh` to stderr.
- `st serve --no-watch` turns the watcher off.

- [ ] **Step 1: Failing tests.**
  - `scheduler waits for a quiet period`: changes at 0, 200 and 400 ms with a quiet time of 500 ms give `due(800) == false` and `due(900) == true`.
  - `scheduler queues another refresh when changes arrive while one runs`: `started()`, then `changed()`, then `finished()` leaves `pending()` true and `due()` true after the quiet time.
  - `watch paths skip build output and delombok copies`.
  - `watch paths fall back to directories above the limit`.
- [ ] **Step 2: Implement.**
- [ ] **Step 3: Smoke.**
  - With a detached server, edit a fixture file and sleep until the server log shows the refresh finished, at most 60 s.
  - The next query's stderr must not contain `refreshed`; its answer must show the edit.
  - Edit again and query at once: stderr shows `waited` or `refreshed`, and the answer is current.
- [ ] **Step 4: Measure** on the bench project: edit one file and query 15 s later. Report the query time; the target is under 200 ms.
- [ ] **Step 5: Commit** `feat(st): st serve watches the sources and refreshes in the background`.

## Not in this plan

- **The ~12 s `Sourcetrail index` refresh itself.** This means the process start, the JVM, the Gradle fingerprint and delombok. The server moves it off the agent's path but doesn't shorten it. Profiling it is the next plan.
- **`st batch`.** A warm server makes per-call startup small. Revisit only if measurements say otherwise.
- **A server serving several projects.**
